画面遷移図
=========================

概要
-------------------------

D2言語を使った画面遷移図の作成方法と設計原則を提供します。
画面種別の視覚的な区別、遷移パターンの表現、レイアウト最適化の手法を体系的に説明します。

適用場面
-------------------------

- UI設計における画面遷移の可視化
- 画面設計書の作成
- ユーザーフロー図の作成
- 開発者間での技術仕様共有
- 自動テスト設計の入力データ
- システム全体の遷移マトリクス検証

基本構造
-------------------------

### 画面遷移図の構成要素

- ノード: 各画面を表現(一覧、詳細、編集、モーダル、処理、外部ページ)
- エッジ: 画面間の遷移を表現(通常遷移、リダイレクト、外部リンク)
- クラス: 画面種別・遷移種別をスタイルで区別
- コンテナ: 必須依存を持つ画面のグループ化(依存先エンティティ配下への配置)

### クラスの命名規則

classesはページ(ノード)用とアクション(エッジ)用の2分類があり、接頭辞で区別する。

- ページスタイル: `page_`接頭辞(例: `page_modal`)
- アクションスタイル: `act_`接頭辞(例: `act_redirect`)

通常画面はスタイル上デフォルトテーマと差がないため、class指定をしない(無指定のままとする)。

### テンプレート

基本構造は[assets/screen_flow_template.d2](../assets/screen_flow_template.d2)を参照してください。

画面種別の表現
-------------------------

### 通常画面

- 用途: 一般的な画面(一覧、詳細、登録、編集など)
- 特徴: class指定なし(デフォルトテーマに委ねる)

```d2
商品一覧
```

### モーダル画面 (page_modal)

- 用途: オーバーレイ表示される画面
- 特徴: 太い枠線で重ね表示を表現

```d2
削除確認: {
  class: page_modal
}
```

### 処理専用画面 (page_process)

- 用途: 背景処理・中継処理を示す画面(削除処理など)
- 特徴: 破線枠で処理のみを表現

```d2
削除処理: {
  class: page_process
}
```

### 外部ページ (page_external)

- 用途: 外部サイト・外部システムへのリンク先
- 特徴: 青系背景+破線枠で外部コンテンツを明示
- ラベル規約: ページ名の後に改行して「(外部)」を付す

```d2
製品元ページ: {
  class: page_external
  label: "製品元ページ\n(外部)"
}
```

遷移種別の表現
-------------------------

### 通常遷移

- 用途: 画面間の標準的な遷移
- 特徴: 実線矢印
- ラベル: ボタンクリック時の操作名を明記(例: 登録、編集、更新、削除)

```d2
商品一覧 -> 商品詳細: 詳細を見る
```

### リダイレクト (act_redirect)

- 用途: 処理完了後の自動遷移
- 特徴: 破線矢印
- ラベル: 省略可、または処理結果を記載(例: 登録完了、削除完了)

```d2
削除処理 -> 商品一覧: {
  class: act_redirect
}
```

### その場更新 (act_inplace)

- 用途: 画面遷移(URL変化・ページ全体の作り直し)を伴わないが、外部通信を伴う更新
    - 更新範囲の大小(部分差し替え/メイン領域丸ごと差し替え)は問わない
    - 実装技術(HTMX、Ajax等)を問わない、実装に依存しない汎用的な表現
- 特徴: 紫系の破線矢印(act_redirectと視覚的に区別)
- ラベル: 更新される操作名を明記(例: 一覧を再取得、検索結果を更新)

```d2
検索フォーム -> 検索結果一覧: {
  class: act_inplace
}
```

### 外部リンク

- 用途: 外部ページへの遷移
- 特徴: 実線矢印+操作名ラベル

```d2
商品詳細 -> 製品元ページ: 製品元へ
```

依存関係の表現
-------------------------

screen-flowスキルで判定した依存関係(必須依存/任意依存、構造的依存/手続き的依存)は、専用のクラスやエッジラベル注記を用いない。
ノードの配置(コンテナのネストの有無)とエッジの張り方だけで表現する。

### 必須依存・構造的依存: コンテナのネスト

対象画面を依存先エンティティのコンテナ内にネストして配置する。多階層の依存がある場合は同様にコンテナを重ねて表現する(再帰適用)。

**重要な制約**: コンテナ外からその画面への直接エッジを引いてはならない。直接エッジが存在すると「依存先の指定なしに到達できる」ことになり、必須依存という前提と矛盾する。

```d2
受注: {
  受注一覧
  受注詳細

  明細: {
    明細一覧
    明細編集
  }
}

受注.受注詳細 -> 受注.明細.明細一覧: 明細を見る
```

### 必須依存・手続き的依存: 通常のエッジの連なり

ウィザード等、一連の処理内で前段の入力が後段の前提になる依存は、通常のエッジを一方向に連ねるだけで表現する。コンテナやラベル注記等の追加表現は不要。

```d2
規約同意 -> 個人情報入力 -> 確認画面 -> 完了
```

### 任意依存: 通常のエッジ(複数可)

対象画面はコンテナの外(独立したノード)として配置し、依存先経由の絞り込み導線を通常のエッジで表現する。依存先を経由しない直接アクセスの動線がある場合は、その分のエッジをもう1本追加するだけでよい。

```d2
メインメニュー -> カテゴリ一覧: カテゴリから探す
カテゴリ一覧 -> 商品一覧: カテゴリで絞り込む
メインメニュー -> 商品一覧: すべての商品を見る
商品一覧 -> 商品詳細: 商品を選択
```

同じ`商品一覧`へ合流する経路は2系統ある。
1つは`メインメニュー -> カテゴリ一覧 -> 商品一覧`(カテゴリーという依存先を経由する経路)をたどる。
もう1つは`メインメニュー -> 商品一覧`(依存先を経由しない直接の経路)をたどる。
この構造で「依存先の指定が必須ではない」ことを表現する。

### 依存関係の判定基準としての副次効果

「コンテナ外からその画面への直接エッジが存在するか」は、作図時に必須依存/任意依存を後から見分ける実質的なチェック基準にもなる。直接エッジが1本でも存在する画面は任意依存として扱い、コンテナ内に配置してはならない。

レイアウト設計
-------------------------

### 全体レイアウト設定

```d2
direction: right
```

左から右へのレイアウトを指定します。

### 画面配置の原則

- **列構成**(左から右)
    - 左列: 一覧画面、モーダル画面、処理専用画面
    - 中列: 詳細画面、編集画面、登録画面
    - 右列: 外部ページ
- 縦方向: 上から下への主要フロー
- 間隔: エッジ交差を最小限に抑える

### エッジの配置

- エッジ交差を極力避ける
- 戻り遷移は画面の左側から出して左回りにする
- 主要フローは左から右、上から下へ配置

実装例
-------------------------

```d2
# 商品管理 画面遷移図
# =========================

direction: right

# ノード定義
商品一覧
商品詳細
商品編集

削除確認: {
  class: page_modal
}

削除処理: {
  class: page_process
}

# エッジ定義
商品一覧 -> 商品詳細: 詳細を見る
商品詳細 -> 商品編集: 編集
商品詳細 -> 削除確認: 削除
削除確認 -> 削除処理: 削除する
削除処理 -> 商品一覧: {
  class: act_redirect
}
商品編集 -> 商品詳細: 更新

# Class定義
classes: {
  page_modal: {
    shape: rectangle
    style: {
      fill: "#FFFFFF"
      stroke: "#CCCCCC"
      stroke-width: 5
      font-size: 14
    }
  }
  page_process: {
    shape: rectangle
    style: {
      stroke-dash: 3
      fill: "#FAFAFA"
      stroke: "#333333"
      font-size: 14
    }
  }
  act_redirect: {
    style: {
      stroke-dash: 3
    }
  }
  act_inplace: {
    style: {
      stroke: "#8E24AA"
      stroke-dash: 6
    }
  }
}
```

設計原則
-------------------------

### 主要フローに集中

- すべての細かい操作を網羅しない
- 戻るボタンなどの標準的な操作は省略可能
- 本質的な画面の流れを明確に表現

### 視覚的な明確性

- 画面種別が一目で区別できるスタイル
- エッジ交差は最小限(3箇所以内を目標)
- 適切な間隔での配置

### 保守性の確保

- Classes定義によるスタイルの共通化
- 個別ノードへの直接的なスタイル設定を避ける
- ページスタイルは`page_`、アクションスタイルは`act_`の接頭辞で統一する
- コメントによる補足説明

Class定義
-------------------------

### 推奨されるclasses定義

**重要**: classes定義はD2ファイルの末尾に配置してください。

```d2
classes: {
  page_modal: {
    shape: rectangle
    style: {
      fill: "#FFFFFF"
      stroke: "#CCCCCC"
      stroke-width: 5
      font-size: 14
    }
  }
  page_process: {
    shape: rectangle
    style: {
      stroke-dash: 3
      fill: "#FAFAFA"
      stroke: "#333333"
      font-size: 14
    }
  }
  page_external: {
    shape: rectangle
    style: {
      stroke-dash: 3

    }
  }
}
```

制約事項
-------------------------

### 禁止表現

- 条件分岐ノード(菱形)は使用しない
- 成功時/失敗時の分岐表現は行わない
- 個別ノードへの直接的なスタイル設定(classを使用すること)
- 通常画面への不要なclass付与(class指定は`page_modal`/`page_process`/`page_external`等、特別な意味を持つ画面のみに限定する)
- 必須依存(構造的)を持つ画面のコンテナ外への配置、およびコンテナ外からその画面への直接エッジ

### 推奨事項

- すべてのエッジに操作名ラベルを付与
- 色は視認性を優先し、アクセシビリティを考慮
- テンプレートから開始してカスタマイズ
- Classes定義はファイル末尾に配置
- ページスタイルは`page_`、アクションスタイルは`act_`の接頭辞で統一する
- 必須依存(構造的)はコンテナのネスト、必須依存(手続き的)は連続エッジ、任意依存は通常エッジで表現する

生成手順
-------------------------

### 1. 入力の分析

画面一覧、遷移パターン、アクター情報を入力として受け取ります。

- 画面一覧から画面名と画面種別を抽出します
- 遷移パターンから遷移元、遷移先、操作名を抽出します
- アクター情報から利用者と権限の違いを整理します

### 2. 画面種別と遷移種別の判定

抽出した情報を本リファレンスの表現へ対応付けます。

- 画面種別は通常画面、`page_modal`、`page_process`、`page_external`を判定します
- 遷移種別は通常遷移、`act_redirect`、`act_inplace`、外部リンクを判定します
- 依存関係は、必須依存(構造的)をコンテナのネストで表現します
- 依存関係は、必須依存(手続き的)を連続エッジ、任意依存を通常エッジで表現します

### 3. レイアウトの設計

`direction: right`を基本とし、画面を左から右へ配置します。

- 依存先エンティティのコンテナへ対象画面をネストします
- すべてのエッジへ操作名ラベルを付与します
- コンテナ外から必須依存の画面へ直接エッジを引かないことを確認します

### 4. 出力

- 出力先は`docs/feature/{機能名}/screen_flow.d2`を既定値とします
- ファイル名は`screen_flow.d2`で固定します
- 呼び出し元の指示がある場合は、その出力先を優先します
