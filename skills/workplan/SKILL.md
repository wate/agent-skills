workplan
=========================

概要
-------------------------

あらゆる作業の実施内容を洗い出し、情報密度を判定したうえで、再開可能で検証可能な作業プランを生成します。

適用場面
-------------------------

以下の場面で活用します。

- `作業プランを作って`、`workplan`、`実施計画を整理したい`を依頼するとき
- 要件はあるが作業分解が未整理で、WBS形式のタスクへ落としたいとき
- 複数セッションや複数担当で再開できる計画が必要なとき

前提条件
-------------------------

本スキルを活用する際は、以下の情報が利用可能であることを確認します。

- 目的、対象範囲、完了条件の少なくとも一部
- 元となる指示書、チケット、会話履歴のいずれか
- 不足情報がある場合は、不足を明示できる状態

役割
-------------------------

作業プラン生成に必要な判断をするため、以下の専門性を前提にします。

- 情報密度判定: 入力内容の完全性と具体性を評価し、対応方針を決定する
- チャット履歴解析: セッション全体から作業状況、技術判断、課題を抽出する
- 作業分解技法(PM技法): WBSに基づいて段階的にタスクを分割し、ネスト構造を管理する
- 暫定計画策定: 不完全情報下で仮定を明示し、段階的に具体化する

仕様
-------------------------

作業プランの構成と書式は、テンプレートを正本として扱います。
見出しの追加、削除、順序変更、記憶による書き換えは禁止します。

### タスクの粒度基準

「実行可能な粒度」を判定するため、以下の2軸でタスクを評価します。理想的には両方を満たす単位で分割します。

#### 検証可能性

1タスクごとに**Doneかどうかが一意に判定できる**こと。

- 判定基準が曖昧なタスクは、完了/未完了の判断が担当者やタイミングによってブレるため、さらに分割する
- 例:悪い「ログイン機能を実装する」→ 良い「ログインフォームを表示する」「認証APIを呼び出す」「エラー時にメッセージを表示する」

#### 影響局所性

1タスクの失敗や変更が、後続タスクのどこまでに影響するかが**構造から判断できる**こと。

- 「設計・選定・方針決定」と「それを前提にした実装」の間にはタスク境界を置き、フラットに分割する。決定内容が後から変わる可能性は、作業プラン作成段階では考慮しない
    - 例:悪い「API仕様を確定し、クライアントを実装する」→ 良い「API仕様を確定する」「クライアントを実装する」
- 複数の末端タスクが同じ完了条件、同じ前提(入力)、同じ制約を共有する場合は、それらをグルーピングし、共通部分を親タスクの下へネストしてまとめる。これにより共通部分の重複記載を避けられる。親タスクには[完了条件のみの簡易カード](#末端タスクの記述基準実行カード)を付与してよい
    - 例:同じ完了条件を持つ複数の末端タスクは、親タスクへまとめる。具体例は下の変換例を参照する
    - 変換例(Before/After):
      Before(悪い例、完了条件が3タスクに重複):

      ```
      - ユーザー一覧APIを実装する
          - 入力: docs/api/users.md#一覧
          - 手順: GET /users を実装する
          - 制約: ページングは対象外
          - 完了条件: 認証エラー時に401を返す
      - ユーザー詳細APIを実装する
          - 入力: docs/api/users.md#詳細
          - 手順: GET /users/{id} を実装する
          - 制約: 論理削除ユーザーは404を返す
          - 完了条件: 認証エラー時に401を返す
      - ユーザー削除APIを実装する
          - 入力: docs/api/users.md#削除
          - 手順: DELETE /users/{id} を実装する
          - 制約: 物理削除は対象外
          - 完了条件: 認証エラー時に401を返す
      ```

      After(良い例、共通の完了条件を親タスクへ1回だけ記載):

      ```
      - 認証エラー時に401を返すAPI群を実装する
          - 完了条件: 認証エラー時に401を返す
          - ユーザー一覧APIを実装する
              - 入力: docs/api/users.md#一覧
              - 手順: GET /users を実装する
              - 制約: ページングは対象外
          - ユーザー詳細APIを実装する
              - 入力: docs/api/users.md#詳細
              - 手順: GET /users/{id} を実装する
              - 制約: 論理削除ユーザーは404を返す
          - ユーザー削除APIを実装する
              - 入力: docs/api/users.md#削除
              - 手順: DELETE /users/{id} を実装する
              - 制約: 物理削除は対象外
      ```

- 分解時点で見落としていた前提が後から覆ることは起こりうる。その場合は本基準への違反ではなく、[新タスク発生時](assets/template.md)の運用(即座に作業プランへ反映し、ユーザーの承認を得てから着手する)に従って作業プランを更新する。これは作業を進める段階の話であり、分解時点で先回りして考慮する必要はない

#### ネスト深さ

- 最大**3階層**まで(大項目 > 中項目 > 小項目)
- 3階層で収まらない場合は、作業範囲自体を別の作業プランへ分割することを検討する

#### 実行可能粒度の基準(低コストモデル/新人)

本スキルにおける実行可能粒度は、特定のベンダーやモデル名ではなく、以下の特性を持つ実行者を基準にする。低コストモデルに限定せず、経験の浅い新人にも同じ基準を当てはめてよい。

- 暗黙の文脈補完をしない、または精度が低い
- 複数ステップの推論チェーンをたどることが不安定
- 曖昧な指示語の解決精度が低い
- 長いコンテキストから必要情報だけを選択的に想起する精度が低い
- 判断の分岐や自由記述の出力形式にばらつきが出やすい

末端タスク(小項目)は、これらの特性を持つ実行者(低コストモデル、または経験の浅い新人)でも実行可能な粒度を目安とする。
判断に迷う場合は、以下の機械的な基準で確認する。

- 対象ファイルが2ファイル以内に収まっているか
- 変更箇所がファイルパス+行番号、関数名、セクション名等で具体的に特定できるか
- 手順文中の動詞が1つだけか(複数の動詞が含まれる場合はさらに分割する)
- 前段タスクへの依存の有無が明記されているか
- 完了条件がコマンドの終了コード、grep件数、テスト結果等、実行結果だけで判定できるか
- 完了条件が[完了条件の強度](#完了条件の強度)における「存在の確認」「部分一致の確認」「状態の記述」に留まっていないか(いずれかに該当する場合は「構造の確認」まで具体化する)

いずれかを満たさない場合は、さらに分割する。

#### 完了条件の強度

完了条件は、機械的に検証できるかどうかだけでなく、検証の強度によって4段階に分けられる。

| 型             | 内容                                                                                       | 危険度       | 理由                                                  |
| -------------- | ------------------------------------------------------------------------------------------ | ------------ | ----------------------------------------------------- |
| 存在の確認     | 対象が作られたかのみを確認する(例: ファイルの存在確認)                                     | 危険         | 中身が空でも条件を満たせる                            |
| 部分一致の確認 | 特定の要素が含まれるかを確認する(例: 特定語句の出現件数確認)                               | 危険         | 該当箇所が1つあれば満たせ、文脈上の妥当性は問われない |
| 状態の記述     | 望ましい状態になっているかを記述する(例:「〜が解消されている」)                            | もっとも危険 | 条件自体が判断であり、実行者が自己判定することになる  |
| 構造の確認     | 定めた形式や必要量を満たしているかを確認する(例: 必須項目の有無、最低文字数、要素数の一致) | 安全         | 機械的に確認でき、判断の余地が入りにくい              |

末端タスクの完了条件は、「構造の確認」の型になるよう具体化する。「存在の確認」「部分一致の確認」で留まっている場合は、対象に必須要素や期待する構造を追加で定義し、それを検証する条件に置き換える。「状態の記述」になっている場合は、その状態を構成する具体的な条件へ分解する。

#### 末端タスクの記述基準(実行カード)

末端タスク(小項目)は、入力/手順/制約/完了条件を持つ実行カード形式で記載する。大項目/中項目はタスク名のみとし、実行カードは付与しない。

ただし、[影響局所性](#影響局所性)に基づき複数の末端タスクをグルーピングする場合、共通の完了条件をまとめる親タスクに限り、完了条件のみを持つ簡易カードを例外として付与してよい。入力/手順/制約は付与せず、末端タスク側にのみ記載する。

- 入力: 参照すべき情報源(ファイルパス、仕様書の該当セクション、既存コード等)
- 手順: 単一の具体的操作。判断や条件分岐を含む複合操作は禁止する
- 制約: 前提となる方針、対象外とする範囲
- 完了条件: コマンドの終了コード、grep結果、テストの成否等、実行結果で機械的に検証できる形で記述する。[完了条件の強度](#完了条件の強度)における「構造の確認」の型になるよう具体化する

実行カードの記述は、以下の基準に従う。

- 1タスク1操作: 判断や条件分岐を含む複合操作を避け、単一の具体的操作のみを記述する
- 曖昧動詞の禁止:「最適化する」「調整する」「適切に実装する」等、解釈幅がある動詞を避け、対象/変更内容/変更後の状態が一意に定まる表現にする
- コンテキストの自己完結: 前タスクの成果を参照する場合、要約や参照リンクではなく、必要な値/パス/内容をタスク内に再掲する
- 完了条件の機械的検証性: 目視判断ではなく、実行結果で判定できる形で記述する
- 出力形式の固定: 自由記述を避け、期待する出力の型(ファイルパス、コード、diff等)を明示する

### テンプレート

#### 手順

1. 出力前に必ずテンプレートを開いて読み込みます。
2. 見出しの文言、順序、階層をテンプレートと一字一句同じものにし、プレースホルダー(`{...}`)部分だけを実際の内容に置き換えます。
3. 出力後、生成した見出し一覧をテンプレートと突き合わせて一致を確認します。

**参照必須**: [作業プランテンプレート](assets/template.md)

以下の項目一覧は所在を示す索引であり、テンプレートの代用にはなりません。

#### 項目一覧

1. 作業プランの使い方
2. 作業指示書情報
3. 不足情報/確認事項
4. 課題・リスク
5. 作業一覧
6. 完了条件
7. 過去の指摘事項・改善点
8. 設計判断ログ
9. 品質基準・注意事項
10. 作業履歴
11. 成果物
12. 関連ファイル

### 出力先

作業プランの内容要件は共通で、保存先と提示方法はAIの種類と実行環境に合わせて切り替えます。
どの環境でも、出力形式は[作業プランテンプレート](assets/template.md)に準拠します。

#### エディタ統合型AI (GitHub Copilot / Claude Code / OpenCode など)

1. ユーザー指定パスがあればそれを優先
2. 指定がなければプロジェクトルート配下の`workplan-*.md`として保存
3. ファイル名は命名規則に従って決定

#### チャット型AI (claude.ai / ChatGPT など)

1. AIの作業領域で提示する (Artifacts、Canvasなど)
2. 作業領域が使えない場合はチャット内にコードブロックで提示する
3. ユーザーが保存先を明示した場合のみ、filesystem MCP経由で保存する

#### 命名規則

- チケット番号あり
    - Redmine: `workplan-ticket-1234.md`
    - Backlog: `workplan-PROJECT-567.md`
    - GitHub: `workplan-issue-1234.md`または`workplan-owner-repo-1234.md`
- チケット番号なし
    - 作業名ベース: `workplan-{作業名}.md`(英数字とハイフン、ケバブケース)
    - 作業名不明: `workplan-YYYY-MM-DD.md`
- 同名ファイル存在時
    - `workplan-{作業名}-2.md`のように連番を付与

### 記載方針

- テンプレートの項目順を維持する
- 次のセッションで再開判断に必要な情報を優先する
- 背景には経緯より判断基準を残す
- 未決事項は未決のものだけを記載し、解決後は決定事項へ移す
- 決定事項には決定内容、理由、影響範囲、根拠を記載する
- 課題とリスクは更新履歴が追える形で残す
- タスクは順序を維持しつつ、状態と進捗を更新する
- 作業一覧では`タスク1`や`タスク1-1`のような固定プレフィックスを使わず、作業内容をそのまま記載する
- 末端タスクは[実行カード](#末端タスクの記述基準実行カード)形式で記載し、大項目/中項目には付与しない
- 作業ログは要点だけに留め、詳細は専用セクションへ寄せる
- 成果物は参照先として開きやすい粒度で列挙する
- 成果物には、作業中に実際に作成、更新、削除したファイルだけを記載する
- 作業プランを作成する作業では、対象となる作業指示の成果物だけを記載し、作業プランファイル自体を成果物に含めない
- 元チケットや参考資料を参照しただけのファイルは成果物へ記載しない
- 削除したファイルは打ち消し線で記載し、末尾に`(削除)`を付ける
- 関連作業プラン・依存関係には別作業プランのみを記載し、自己参照リンクを記載しない
- 不足情報/確認事項には、情報不足で計画を具体化できない場合に必要な情報や、自明でない推測・仮定を記載する。確認事項が解消されたら削除するか「なし」と記載する
- 課題・リスクは現時点で未解決または要監視の項目を優先して記載し、リスクの度合いが高い順(高→中→低)に並べる。解消済み項目は打ち消し線を残すか作業履歴へ移動し、完全に不要となった項目を削除する場合は削除した旨を作業履歴に残す
- 設計判断ログにはユーザーが下した、またはユーザーが明示的に承認した判断のみを理由とともに時系列で記録し、課題・リスクの状態管理とは分離する。AIが確認を経ずに独自に下した判断は記載しない
- 品質基準・注意事項には品質基準や留意点、作業中に判明した技術的注意点を箇条書きで記載する
- 過去の指摘事項・改善点には分類ごとに指摘内容と対応方針を記載する

手順
-------------------------

### Step 1: 情報を収集して判定する

1. 作業の原点となる文書の有無を確認する
    - Markdown形式の作業指示書やチケット
    - プロジェクト管理ツールの情報(Redmine、Backlog、GitHub Issuesなど)
2. チャット内の指示内容、チケット番号、URL、Issue番号の有無を確認する
3. 「これまでのチャット」などの表現がある場合は、現在のセッション全体を参照する
    - 完了タスクと未完了タスクを抽出する
    - 作業の背景、目的、技術的判断を整理する
    - 発生した課題と解決方法を記録する

#### 情報密度を判定する

必須3項目で情報密度を判定します。

| #   | 必須項目     | 確認内容                     |
| --- | ------------ | ---------------------------- |
| 1   | 目的・ゴール | 何を達成するかが明確         |
| 2   | 対象範囲     | 何をどこまで実施するかが明確 |
| 3   | 完了条件     | Doneの定義が明確             |

補助項目として、前提条件・制約条件、入力情報源の参照可否、実装方法(How)の方向性も確認します。

##### 判定ルール

- 必須3項目すべて明確: 情報十分と判定し、「情報が十分な場合」へ進む
- 必須3項目に不明確なものを含む: 情報不足と判定し、「情報が不足している場合」へ進む
- 意図自体を読み取れない: 「意図が読み取れない場合」へ進む

#### Step 1 完了チェック

- [ ] 情報密度判定結果(十分/不足/不明)を記載した
- [ ] 判定理由を「何が明確で、何が不足か」で記載した
- [ ] チャット履歴参照の指示がある場合、セッション全体を参照した

### Step 2: 情報密度別に対応する

#### 情報が十分な場合

1. チケットのHow記述を作業分解に反映する
2. WBSベースで[タスクの粒度基準](#タスクの粒度基準)に従ってタスクを分解し、依存関係と前提条件を明記する。末端タスクは[実行カード](#末端タスクの記述基準実行カード)形式で記述する
3. 完了条件を定義する
4. 不足情報/確認事項は空または「なし」と記載する
5. チャット履歴参照時は作業履歴へ今回セッションを記録する

#### 情報が不足している場合

不足情報ごとに以下を判定して対応します。

- ユーザー確認が必須の不足
    - チケット末尾へ不足情報/確認事項を追記して補完を依頼
- 技術調査で解決可能な不足
    - 最初のタスクに調査・設計を置いた作業プランを生成
- 両方ある不足
    - ユーザー確認項目は追記し、調査可能項目は作業プランへ組み込む

#### 意図が読み取れない場合

1. 作業プラン生成前に、目的、対象範囲、前提条件、期待成果物を質問する
2. 回答後に作業プランを生成する
3. 回答が得られない場合は骨組みのみ生成し、不足情報/確認事項へ質問事項を記載する

#### Step 2 完了チェック

- [ ] 情報不足や推測がある場合は不足情報/確認事項に明示した
- [ ] 作業分解のチェックボックスが3階層以内であることを確認した
- [ ] 作業一覧に`タスク1`形式の固定プレフィックスが含まれていないことを確認した
- [ ] タスクが実行可能な粒度に分解され、依存関係が明確である
- [ ] 完了条件が検証可能な記述になっていることを確認した
- [ ] 末端タスクの完了条件が[完了条件の強度](#完了条件の強度)における「構造の確認」の型になっていることを確認した(「存在の確認」「部分一致の確認」「状態の記述」に留まっていないか)
- [ ] 末端タスクが実行カード形式(入力/手順/制約/完了条件)で記載されている
- [ ] 完了条件をグルーピングした親タスクがある場合、完了条件のみの簡易カードになっている(入力/手順/制約を含んでいない)
- [ ] 末端タスクの手順が単一操作になっている(判断・条件分岐を含まない)
- [ ] 末端タスクの完了条件が機械的に検証可能な記述になっている
- [ ] 前タスクの成果を参照する場合、要約せず必要な情報を再掲している

### Step 3: 作業プランファイルを生成する

1. テンプレートに沿って作業プランを生成する
2. 情報密度判定結果に応じて内容を記載する
3. 推測を置いた場合は不足情報/確認事項に根拠つきで明示する
4. 関連ファイルに元チケットとチェックリストのリンクを記載する(存在する場合)
5. 元チケット側の関連ファイル欄にも、この作業プランへのリンクを追記する(存在する場合)

#### Step 3 完了チェック

- [ ] テンプレートの全セクションを適切に記載した
- [ ] 課題・リスクの更新ルール(解消時の打ち消し線/履歴移動/削除記録)を運用手順として記載した
- [ ] 関連ドキュメント更新の有無を確認し、必要な場合はタスクとして追加した
- [ ] 推測や仮定を置いた場合は、不足情報/確認事項に根拠を記載した
- [ ] 成果物セクションに、作業中に実際に作成、更新、削除したファイルを記載した
- [ ] 作業プランを作成する作業では、対象となる作業指示の成果物だけを記載し、作業プランファイル自体を成果物に含めていない
- [ ] 成果物がない場合は`なし`と記載した
- [ ] 成果物セクションに、参照のみで未編集のファイルが含まれていない

### Step 4: チェックリストと突き合わせる

2. 実装漏れと過剰実装を検出する
3. 実装漏れはタスク追加で補完し、過剰実装はユーザー確認する
4. 問題がなければ「チェックリスト突き合わせ: 問題なし」と記載する

制約・禁止事項
-------------------------

### 技術的制約

- テンプレート構造を厳守する
- エディタ統合型AIでは、ユーザー指定パスがない場合にプロジェクトルート配下へ保存する
- 命名規則はケバブケースを使用し、日本語とスペースを使用しない

### 品質制約

- 推測で情報を補完せず、不足情報を明示する
- すべてのタスクを[タスクの粒度基準](#タスクの粒度基準)に従って記載する
- 末端タスクは[実行カードの記述基準](#末端タスクの記述基準実行カード)(1タスク1操作、曖昧動詞の禁止、コンテキストの自己完結、完了条件の機械的検証性、出力形式の固定)に従う
- 用語と表記を統一し、矛盾を作らない

### 禁止事項

- 情報不足を推測で埋めること
- 「これまでのチャット」指定を無視して直近だけ見ること
- チェックボックスを4階層以上で運用すること
- チケットやチェックリストが存在するのに関連ファイルリンクを省略すること
- テンプレートファイルを読まずに作業プランを出力すること
- テンプレートと異なる見出し構造や記法で出力すること
- テンプレートにないセクションを追加すること

出力フォーマット
-------------------------

作業プランの構造は[作業プランテンプレート](assets/template.md)を正本とし、[項目一覧](#項目一覧)に示した項目順で出力します。項目リストの再掲は行いません。
出力前に必ずテンプレートファイルを読み、見出し構造と記法を一致させます。テンプレートにないセクションは追加しません。
