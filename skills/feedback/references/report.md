feedbackの記録の集計レポート
============================

`.github/feedback/`の記録のうち、feedback・project・referenceの3カテゴリーを集計し、反映と削除の判断材料をそろえたレポートを生成する手順です。
集計と報告までを担当し、反映先の実ファイル更新と記録の削除は行いません。
`user`カテゴリーは対象外とします。

実行手順
-------------------------

1. 対象期間を確認します。
2. 保存ディレクトリの`feedback_*.md`・`project_*.md`・`reference_*.md`を全件読み込みます。
    - 各ファイルのフロントマター(`name`・`description`・`metadata.type`)と本文を抽出します。
3. feedbackは、判定ルールに従ってSSOT重複確認を行ってから各項目を分類します。
4. project・referenceは、判定ルールに従ってSSOT確認を行ってから反映要否を付与します。
5. 同種の内容は、再発傾向・関連項目としてまとめます。
6. 出力仕様に従い、サマリーと個票をMarkdown形式で整形します。

### 読み取る項目

- フロントマター: `name`(識別名)、`description`(一行要約)、`metadata.type`(カテゴリー)をそのまま使います。
- 本文: 事実・ルール本体、Why(理由)、How to apply(発動条件)を抽出します。
- project・referenceは本文の構成が異なる場合があるため、該当する記述がなければ空欄として扱います。

判定ルール
-------------------------

feedbackとproject・referenceでは判定方式が異なります。
判定ルールの変更は、この節だけを差し替えれば済むようにします。

### SSOTの確認先

次のうち、プロジェクトに存在するものを確認します。
存在しないものは飛ばします。

- `.github/copilot-instructions.md`
- `AGENTS.md`
- `.github/instructions/`
- `docs/`
- `.github/skills/*/SKILL.md`

### feedbackの判定ルール

2値判定の前に、SSOTの確認先へ同趣旨の規定がすでにあるかを確認します。

- 原本がある場合:「反映済み・削除候補」に分類し、2値判定・重要度・反映先は付与しません。
    - 二重管理を避けるため、元の`feedback_*.md`と`index.md`の該当行を削除対象として扱います。
- 原本がない場合: 次の2値判定へ進みます。

判定は`反映する / 要検討`の2値です。

- 反映する: 再発防止のため、開発/作業プロセスまたはレビュースキルへ反映すべきもの
- 要検討: 1件だけでは一般化しづらく、類似指摘が増えた段階で判断するもの

反映先は`開発/作業プロセス / レビュースキル / スキル・ドキュメント / 両方`のみを使います。

- 開発/作業プロセス: 実行前から提出前のセルフチェックまでに、手順・確認タイミング・ルール化で防ぐべきもの
- レビュースキル: 実装後の差分・挙動を**第三者が**確認して検出すべきもので、セルフチェックは含めない
- スキル・ドキュメント: 特定の`SKILL.md`や開発ドキュメントの内容を修正すべきもの
- 両方: プロセスで防ぎたいが、すり抜けた場合に第三者レビューでも別の観点で独立して検出できるもの

反映先カテゴリーを選んだら、実際のリポジトリ構成を確認して、反映すべき実ファイルを1つ特定します。
候補が複数ある場合は、本文への適合がもっとも高い1件を選び、判断理由を添えます。

判定が「反映する」の項目には、重要度を`最重 / 高 / 中 / 低`で付与します。

- 最重: 単発でも重大事故につながるもの(権限逸脱、法令違反、データ破壊)
- 高: 影響範囲や復旧コストが大きいもの
- 中: 再発すると品質低下が蓄積するもの
- 低: 影響が局所的で、標準手順で吸収できるもの

### project・referenceの判定ルール

2値判定のバケットは設けず、全項目へ反映要否を付与して反映先提案リストへ記載します。
重要度は付与しません。

反映要否の判定の前に、対象ドキュメントへ同趣旨の記載がすでにないかを確認します(SSOT確認)。
反映要否は`反映する / 反映不要 / 判断待ち`のみを使います。

- 反映する: 反映先ドキュメントに未記載で、反映の必要があるもの
- 反映不要: 反映先または同一領域の資料に同趣旨の記載がすでにあるもの(既存記載の所在を添える)
- 判断待ち: 反映する価値はあるが必須でないもの

項目ごとに、反映先を1件提案する文を「〇〇というドキュメントへの反映(新規作成を含む)を検討してください」の形式で作ります。
反映先は次の順で判断します。

1. 成果物一覧やドキュメント依存関係表に相当するものがあれば、それを参照して該当する成果物名を提案する
2. ない場合や該当がない場合は、一般的なドキュメント構成(README、要件定義書、設計書等)から妥当な反映先を提案する
3. いずれでも特定できない場合は「反映先未定」と記載し、理由を添える

特定のファイル名・表名を前提とせず、都度実際のリポジトリ構成を確認して判断します。

### 共通ルール

- 値域外の値や判定不能な項目は「要確認データ」として報告します。
- フロントマターが欠損している、または`metadata.type`が対象外の値であるファイルは、除外せず「要確認データ」として記載します。
- 判定不能な項目は推測で確定せず、「要追記ルール」として人の判断待ちにします。

出力仕様
-------------------------

### 必須出力項目

タイトル直下に「このレポートの使い方」を置き、各判定バケットと反映要否の後続対応を箇条書きで示します。
反映・削除はこのレポートでは行わず、後続の指示で実施する旨も含めます。

1. 集計サマリー
    - 総件数、カテゴリー別件数、feedbackの判定別件数(反映する/要検討/反映済み・削除候補)、feedbackの反映先別件数
    - project・referenceの反映要否別件数(反映する/反映不要/判断待ち)
2. feedback反映候補(優先順)
    - 判定が「反映する」の項目を、重要度(最重、高、中、低の順)で並べる
    - 各項目に「事実・ルール本体」「Why」「How to apply」「重要度」「反映先」「反映先ファイル」を記載する
    - 反映先ファイルを特定できない場合は「反映先ファイル未定」と理由を添える
3. feedback要検討リスト
    - 判定が「要検討」の項目を、反映先を付けずに列挙する
    - 類似指摘が増えた段階で再評価する理由を補足する
4. feedback反映済み(削除候補)リスト
    - 各項目に「事実・ルール本体」「既存原本の所在」「削除対象(`feedback_*.md`と`index.md`の該当行)」を記載する
5. project・reference反映先提案リスト
    - 各項目に「事実・ルール本体」「Why」「How to apply」(記載があれば)、「反映先提案文」「反映要否」を記載する
    - 反映要否が「反映不要」の場合は、既存記載の所在を添える

セクションの順序は固定し、差分を比較しやすくします。

### 出力例

上記の必須出力項目は索引であり、書式の正本は出力例とします。
出力前に必ず[assets/report-sample.md](../assets/report-sample.md)を読み込み、見出し構成と書式を一致させます。
出力後は、生成した見出しを出力例と突き合わせ、追加・削除・順序変更がないことを確認します。
見出しの文言・順序・階層は記憶で書き換えず、出力例を正本として扱います。
必須出力項目と出力例が矛盾する場合は、記載内容は必須出力項目、書式は出力例を優先します。

### 出力先と命名規則

- 出力先: プロジェクトルート
- ファイル名: `report-feedback-YYYYMMDD.md`
- 同日に再生成する場合は、末尾に`-v2`のような連番を付けます。

品質確認
-------------------------

- 対象: feedback・project・referenceを対象にし、`user`を含めていない
- 件数: レポートの記載件数と元の記録の件数が一致している
- feedbackの判定: 全件に判定が付与され、「反映する」の項目には重要度・反映先・反映先ファイルが付与されている
- 要検討: 判定が「要検討」の項目に反映先を付与していない
- SSOT重複確認: feedback全件で確認し、原本がある項目は「反映済み・削除候補」に分類している
- project・referenceの判定: 全件に反映先提案文と値域内の反映要否が付与され、「反映不要」には既存記載の所在が添えられている
- 表記: 重要度が「最重/高/中/低」の日本語表記で統一されている
- 境界: レポート内で自動反映を指示していない

禁止事項
-------------------------

- feedbackの「反映する」を自動で確定し、実装まで進めること
- project・referenceの反映先を自動で確定し、ドキュメント更新まで進めること
- SSOT確認を経ずに、反映候補や反映要否を確定すること
- 実ファイルを確認せずに反映先ファイルを確定すること
- 根拠なしに重要度を引き上げること
- 未確認データを確定情報として扱うこと

エラーハンドリング
-------------------------

- feedbackの記録が見つからない: 保存ディレクトリの存在確認を促し、空のレポートは生成しません。
- 形式不整合が混在する: 当該項目を「要確認データ」へ分離し、件数と内容を記載します。

セキュリティ
-------------------------

- 記録内の機密文字列はマスクして出力します。
- 個人情報は識別できる部分を伏せます。
