Claude メモリ機構リファレンス
=============================

このドキュメントは、Claude本体が持つメモリ機構の仕様をまとめたものです。
memoryスキルをfeedbackスキルから発展させる際の設計リファレンスとして使用します。
内容はClaudeに与えられているシステム指示を整理したものであり、
そのままの再現ではなく、本プロジェクトの運用へ取り込む観点で参照します。

保存場所と構成
-------------------------

メモリはグローバル領域にプロジェクト単位で保存します。

- 保存ディレクトリ: `~/.claude/projects/<プロジェクト識別子>/memory/`
- 索引ファイル: `MEMORY.md` をディレクトリ直下に必ず1つ置きます
- 個別メモリ: `<name>.md` として1メモリを1ファイルで保存します

カテゴリー
-------------------------

メモリは4種類の排他的なカテゴリーで分類します。

> 注記: 本プロジェクトのfeedbackスキルは、本節の4カテゴリー構成をそのまま採用します。

- `user`: ユーザーの役割、目的、責任範囲、既有知識。説明の粒度や前提を相手へ合わせるために使います。
- `feedback`: AIへの是正指摘に加え、検証済みで非自明な判断の追認も含みます。同じ指摘の再発を防ぎ、過去の妥当判断からのズレも防ぐために使います。
- `project`: 進行中の作業、決定事項、締切、背景のうち、コードから読み取れないもの。依頼の動機を汲んだ提案をするために使います。
- `reference`: チケット管理やダッシュボードなど外部システムの参照先。外部情報が必要な場面で在り処を示すために使います。

次のものは保存しません。理由は、より信頼できる正本が別に存在するためです。

- コードパターン、アーキテクチャ、ファイル配置。コードそのものが正本です。
- 変更履歴や変更者。git logとgit blameが正本です。
- デバッグの解法。コードとコミットメッセージが正本です。
- CLAUDE.mdにすでに書かれている内容。
- 進行中タスクの一時的な状態。

個別メモリファイルの形式
-------------------------

各メモリファイルはフロントマターと本文で構成します。

```markdown
---
name: kebab-case-slug
description: 一行要約。将来の関連度判定に使うため具体的に書く
metadata:
  type: user|feedback|project|reference
---

本文。
```

- descriptionは将来の関連度判定に使うため、具体的に書きます。
- feedbackとprojectのタイプは、本文を3段構成にします。
    - 事実またはルール本体
    - `**Why**:` として理由や経緯を書く
    - `**How to apply**:` として発動条件を書く
- 理由を残すことで、将来のエッジケースでも応用が利きます。
- 関連メモリは `[[other-name]]` でリンクします。リンク先が未作成でも、将来書く印として許容します。

> 注記: 本プロジェクトのfeedbackスキルでは、上記は次の形式へ変更して運用します。
>
> - `**Why**:`等のインライン太字ラベルは、見出しの下に本文が続くMarkdown構造と曖昧になるため、`Why`と`How to apply`をh2セクション化します
> - `[[other-name]]`のwikiリンクは、`- [メモリのタイトル](ファイル名) - 要約`のMarkdownリンクへ置き換えます
>
> 現行仕様は[SKILL.md](../SKILL.md)を参照してください。

索引ファイル
-------------------------

`MEMORY.md` はメモリ全体の目次として機能します。

- フロントマターは持たず、1行1メモリの一覧のみを記載します。
- 記法は `- [タイトル](file.md) — 一言フック` とし、1行150文字以内に収めます。
- セッション開始時にコンテキストへ自動で読み込まれ、想起の起点になります。
- 分量が増えると切り詰められるため、索引自体は簡潔さを最優先します。

書き込みトリガー
-------------------------

次の場面で保存を判断します。

- ユーザーが明示的に記憶を指示した場合。種別を判断して保存します。
- 是正や指摘を受けた場合。feedbackとして保存します。
- 非自明な選択が反論なく受け入れられた場合。feedbackとして追認を保存します。指摘だけを拾うと過去の妥当判断からズレるため、ここを見落とさないようにします。
- 役割、背景、外部参照に関する新情報を知った場合。該当カテゴリーへ保存します。
- 「忘れて」と指示された場合。該当ファイルを探して削除します。

保存前に既存メモリを検索し、重複がある場合は新規作成せず既存ファイルを更新します。

想起の仕組み
-------------------------

想起はハーネス側の自動注入に依存します。ここがスキル単体では再現しづらい部分です。

- セッション開始時に `MEMORY.md` 全体がシステムプロンプトへ自動注入されます。AIが自発的に探しに行くのではなく、毎回強制的に読み込まれます。
- 会話の進行で個別メモリが必要になった場合、索引の一覧から該当ファイルを読みます。索引から詳細への2段引きです。
- コンテキスト圧縮や履歴クリアをまたいでも `MEMORY.md` は再注入されます。

陳腐化への防御
-------------------------

メモリの記述は書かれた時点の主張であり、現時点の事実の保証ではありません。

- ファイルパスは使用前に実在を確認します。
- 関数名やフラグ名はgrepで確認します。
- 現在の状態を問われた場合は、記憶よりもgit logやコードを優先します。

定期整理の仕組みもあり、重複のマージ、誤りの修正、索引の刈り込みを行います。

他の永続化手段との使い分け
--------------------------

メモリは未来のセッションでも価値がある知識だけを対象にします。

- Plan: 着手前の合意形成に使い、完了後は破棄します。メモリには入れません。
- Tasks: セッション内の作業分解と進捗に使う一時的なものです。メモリには入れません。
- Memory: 将来のセッションでも参照価値がある知識のみを保存します。

memory スキル設計への対応づけ
-----------------------------

本機構と、本プロジェクトで検討中のmemoryスキルは次のように対応します。

- 索引ファイル `MEMORY.md` は、AGENTS.mdの継続的改善セクションが担う想起導線に対応します。
- カテゴリー別の保存は、検討中のカテゴリー別ログファイル方針とほぼ同じ発想です。
- 指摘だけでなく非自明な追認も拾う方針は、重要と判断したものを自ら記録する運用に対応します。
- 保存前に重複を検索して更新する方針は、feedbackスキルの重複排除ロジックと同じ設計思想です。
