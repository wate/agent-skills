feedback
=========================

概要
-------------------------

このスキルは、AIとユーザーの協業で得られた知識を4カテゴリーに分類して永続化し、セッションをまたいで想起するメモリ管理フレームワークです。

### 主な特徴

- 自律記録: ユーザーの明示的な呼び出しがなくても、記録すべき場面でAIが自ら判断して記録する
- 4カテゴリー: user・feedback・project・referenceへ排他的に分類する
- 個別ファイル: 1メモリを1ファイルで保存し、索引ファイル`index.md`から一覧を把握する
- 重複排除: 保存前に既存メモリを検索し、重複がある場合は新規作成せず既存ファイルを更新する
- 陳腐化への防御: 記述は書かれた時点の主張であり、現在の事実確認にはgrepやgit logを優先する

カテゴリー
-------------------------

メモリは以下4種の排他的なカテゴリーで分類します。

- `user`: ユーザーの役割、目的、責任範囲、既有知識。説明の粒度や前提をユーザーへ合わせるために使う
- `feedback`: AIへの是正指摘に加え、検証済みで非自明な判断の追認も含む。同じ指摘の再発を防ぎ、過去の妥当判断からのズレも防ぐために使う
- `project`: 進行中の作業、決定事項、締切、背景のうちコードから読み取れないもの。依頼の動機を汲んだ提案をするために使う
- `reference`: チケット管理やダッシュボードなど外部システムの参照先。外部情報が必要な場面で在り処を示すために使う

### 保存しないもの

以下はより信頼できる原本が別に存在するため保存しません。

- コードパターン、アーキテクチャ、ファイル配置(コードそのものが原本)
- 変更履歴や変更者(git log、git blameが原本)
- デバッグの解法(コードとコミットメッセージが原本)
- AGENTS.mdにすでに書かれている内容
- 進行中タスクの一時的な状態

記録トリガー
-------------------------

次の場面で保存を判断します。手動呼び出しは補助的な位置づけとして引き続き受け付けます。

### AIが自律的に記録すべき場面

- ユーザーが明示的に記憶を指示した場合。種別を判断して保存する
- 是正や指摘を受けた場合。`feedback`カテゴリーとして保存する
- 非自明な選択が反論なく受け入れられた場合。`feedback`カテゴリーとして追認を保存する(指摘だけを拾うと過去の妥当判断からズレるため見落とさない)
- 役割、背景、外部参照に関する新情報を知った場合。該当カテゴリーへ保存する
- 「忘れて」と指示された場合。該当ファイルを探して削除し、`index.md`の対応する行も削除する

### ユーザーの承認を得る場合

- 軽微な指摘(命名規則の微妙な違反、好みの問題等)
- 主観的な判断が必要なもの(可読性、設計の好悪等)
- 記録すべきか判断に迷う場合

### 呼び出し方法(補助)

ユーザーは次の形で明示的な記録を指示できます。

- 「これを記憶しておいて」
- 「このプロジェクトの決定事項として記録して」
- 「このURLを参照先として覚えておいて」

保存前の重複チェック
-------------------------

新規保存の前に、保存先カテゴリーの既存メモリファイルを検索します。

- 照合条件: 対象と同じ趣旨のメモリがすでに存在するか(`name`・`description`・本文の主旨で判定)
- 一致する場合: 新規作成せず、既存ファイルの本文を更新する。更新によって内容の要旨が変わった場合は`index.md`の対応行(発動条件フック)も合わせて更新する
- 一致しない場合: 新規ファイルを作成する

保存後のフック確認
-------------------------

VS Code Copilot Chatで動作している場合は、メモリを保存するたびに、想起用のSessionStartフックが登録済みかを確認します。
フックが未登録のままだと、保存したメモリが次のセッションで想起されないためです。
VS Code Copilot Chat以外のエージェントで動作している場合は、何もしません。

1. プロジェクトルートで、このスキルのディレクトリ配下の`scripts/vscode-copilot/setup-hook.mjs`を`--check`付きで実行する
    - 次の例は、スキルを`.agents/skills/feedback/`に置いた場合である

      ```sh
      node .agents/skills/feedback/scripts/vscode-copilot/setup-hook.mjs --check
      ```

2. 終了コードに応じて対応する
    - 0(登録済み): 何もしない
    - 2(未登録): フックを登録してよいかを利用者へ1回だけ確認する。承認されたら`--check`を外して同じスクリプトを実行する
    - 3(内容が異なる): 上書きせず、表示された差分を利用者へ示して判断を戻す
    - 1(エラー): 出力されたエラー内容を利用者へ伝える
3. 登録した場合は、VS Codeの再起動またはフック設定の再読み込みの後に有効になる旨を利用者へ伝える

登録を断られた場合は、同じセッションでは再確認しません。
`.github/hooks/`はリポジトリで共有する設定のため、利用者の確認なしに書き込まないこと。

feedbackの記録の精査
-------------------------

`.github/feedback/`の記録がたまったら精査し、原本へ反映済みのものを削除して索引を小さく保ちます。
精査の集計手順は[references/report.md](references/report.md)にあります。

### 集計手順を読み込むタイミング

- 利用者からfeedbackの記録の精査や集計を依頼されたとき
- 次の「精査の提案」が承認されたとき

自律記録のために発動した場面では、集計手順を読み込みません。

### 精査の提案

feedbackの記録を保存した直後に、次の手順で精査を提案するかを判断します。

1. `index.md`の一覧のうち、`user_`で始まるファイルを除いた行数を数える
2. 20件(目安)未満なら、何もしない
3. 20件以上なら、精査を1回だけ利用者へ提案する
    - 提案では「`.github/feedback/`の記録」と保存先を示し、エージェント自身のメモリ機能と区別できるようにする
4. 承認されたら、`references/report.md`に従って集計レポートを作る

提案と集計レポートの作成までを行い、反映と記録の削除は利用者が決めます。
提案を断られた場合は、同じセッションでは再提案しません。

保存レイアウト
-------------------------

- 保存ディレクトリ: `.github/feedback/`
- 索引ファイル: `.github/feedback/index.md`をディレクトリ直下に必ず1つ置く
- 個別メモリ: `.github/feedback/<type>_<name>.md`として1メモリを1ファイルで保存する。`<type>`はカテゴリー名、`<name>`はkebab-caseスラッグ

個別メモリファイルの形式
-------------------------

各メモリファイルはフロントマターと見出し付きの本文で構成します。

```markdown
---
name: kebab-case-slug
description: 一行要約。将来の関連度判定に使うため具体的に書く
metadata:
  type: feedback
---
メモリのタイトル
=========================

ルールや事実の本体。

Why
-------------------------

理由や経緯。

How to apply
-------------------------

発動条件や適用方法。
```

- h1にはメモリのタイトルを書き、フロントマターの`description`と主旨を揃える
- `metadata.type`はカテゴリー節の4種から選ぶ
- feedbackとprojectのタイプは、h1の直後にルールや事実の本体を書き、続けて`Why`と`How to apply`のh2セクションを置く
    - `Why`: 理由や経緯
    - `How to apply`: 発動条件や適用方法
- referenceのタイプは上記構成の適用外とし、参照先とその取得方法を書く
- 関連するメモリがある場合は、末尾に`関連`のh2セクションを置く
    - 記法は`- [メモリのタイトル](ファイル名) - 関係の要約`とする
    - リンク先が未作成でも、将来書く印として許容する

索引ファイル`index.md`
-------------------------

`index.md`はメモリ全体の目次として機能します。

- フロントマターは持たない
- 先頭にh1見出し(索引タイトル)を置き、続けて想起指示の誘導文を固定で1つ置き、その後に一覧を記載する
    - 誘導文は「作業内容の確定直後に索引を再走査し、該当する発動条件があれば着手前に本文を必ず読む」旨を命令形で書く
    - 誘導文を`index.md`側に置くのは、フック・`instructions`設定・AGENTS.md方式のいずれの想起経路でも`index.md`が読み込まれ、全経路へ一律に効かせるためである
- 各行の記法は`- [メモリのタイトル](ファイル名) - 発動条件 -> 参照先`とし、1行150文字以内に収める
    - フックには結論の要約ではなく発動条件を書く。要約だけで用が足りると誤認させ、本文の読み込みを妨げないため
- 新規メモリを保存したら、必ず対応する1行をこのファイルへ追記する
- 索引を見て関連しそうなエントリがあれば、個別ファイルを読みに行く(2段引き)。セッション開始時に限らず、作業内容が判明した時点でも都度行う

想起導線
-------------------------

各コーディングエージェントへの組み込み方法は以下の通りです。

- [references/recall-integration.md](references/recall-integration.md)

登録はセットアップスクリプトで自動化できます。
実行前の確認事項とオプションは、上記の組み込み方法を参照します。

- VS Code Copilot Chat: `scripts/vscode-copilot/setup-hook.mjs`(SessionStartフックを`.github/hooks/feedback.json`へ登録)
- opencode: `scripts/opencode/setup-instructions.mjs`(`instructions`設定へ登録)

スキルを`.agents/skills/feedback/`へ置いた場合、VS Code Copilot Chat向けはプロジェクトルートで次のように実行します。

```sh
node .agents/skills/feedback/scripts/vscode-copilot/setup-hook.mjs
```

陳腐化への防御
-------------------------

メモリの記述は書かれた時点の主張であり、現時点の事実の保証ではありません。

- ファイルパスは使用前に実在を確認する
- 関数名やフラグ名はgrepで確認する
- 現在の状態を問われた場合は、記憶よりもgit logやコードを優先する

セキュリティ上の注意
-------------------------

- 機密情報の値(APIキー、パスワード、個人情報等)は記録しない
- 指摘自体は記録し、値は`[REDACTED]`で置換する
