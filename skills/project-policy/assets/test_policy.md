テスト方針
=========================

{プロジェクト名}のテストにおける方針と基準を定めます。
基準を満たすための手順は、手段の概要から参照する手順書に置きます。

方針
-------------------------

### テスト戦略

テストピラミッドに従い、下の層ほど厚く、上の層ほど薄くテストを実装します。

- ユニットテスト: もっとも多く実装し、高速に実行できる層とします。
- インテグレーションテスト: 主要な連携部分を検証する層とします。
- E2Eテスト: 重要なユーザーシナリオだけを実装する層とします。

リソースが限られる場合は、次の優先順位でテストを実装します。

1. セキュリティ関連機能: 認証、認可、データ保護
2. ビジネスクリティカル機能: 決済、重要なデータ操作
3. コア機能: 主要な業務フロー
4. 補助機能: その他の機能

### テスト設計の考え方

テストの質は、実装件数ではなく、洗い出した業務フローとテストパターンを網羅しているかで判断します。
「N件パス」は網羅性の指標にならないため、補足情報として扱います。

バックエンドテストとE2Eテストは相補関係にあり、一方で他方を代替できません。
バックエンドテストはサーバーの応答を保証し、E2Eテストはユーザーが正しく操作できることを保証します。

### 品質の考え方

カバレッジやテスト実行時間は、品質を可視化する手段です。
数値目標の達成自体を目的としません。

カバレッジが低くても、重要な機能が十分にテストされていれば許容します。
カバレッジが高くても、形骸化したテストは許容しません。

基準
-------------------------

### テスト設計の基準

テスト実装の完了は、次のすべてを満たすこととします。

- 洗い出したテストパターンがすべて実装されている
- 未実装のパターンがある場合、その理由と対応方針が明記されている
- 変更に関係するテストがパスしている
- バックエンドテストとE2Eテストの住み分けが守られている

変更と無関係な既存テストの失敗は、完了の妨げとしません。
ただし失敗内容と、今回の変更が原因ではないと判断した根拠を報告します。

レイヤーごとに検証できる範囲は次のとおりです。

| レイヤー           | 検証できること                                                          | 検証できないこと                         |
| ------------------ | ----------------------------------------------------------------------- | ---------------------------------------- |
| バックエンドテスト | レスポンスコード、リダイレクト、Flashメッセージ、データベースの書き込み | ブラウザ上の表示結果、ユーザー操作の結果 |
| E2Eテスト          | ページ遷移、フォームの表示と送信、動的な画面変化、複数画面の操作        | 検証対象外のブラウザやデバイスでの動作   |

### 品質基準

リリース可否は、次の観点で総合的に判断します。

必須条件は次のとおりです。

- クリティカルなバグが存在しない
- セキュリティ関連の重大な問題が解決されている
- 主要機能のテストが完了している

あわせて、次の水準を満たすこととします。

- ユニットテストカバレッジが{ユニットテストカバレッジ目標}以上
- 自動テストの成功率が{自動テスト成功率}以上
- {対応ブラウザ}での主要シナリオの動作確認が完了している

テスト失敗時は、影響範囲と重要度に応じて対応します。

| 重要度 | 判断基準                           | 対応                                 |
| ------ | ---------------------------------- | ------------------------------------ |
| 緊急   | データ損失、セキュリティ侵害の恐れ | リリースを止め、即座に対応する       |
| 高     | 主要機能が使用不可                 | 優先的に修正し、影響範囲を確認する   |
| 中     | 一部機能に制限                     | 状況に応じて判断し、回避策も検討する |
| 低     | 使用上の支障が少ない               | 計画的に対応する                     |

次の指標を測定し、品質改善に使います。

- テストカバレッジ
- テスト実行時間
- 欠陥傾向

### ユニットテストの基準

カバレッジの目安は次のとおりです。

| カバレッジ率                                                 | 評価     | 考え方                         |
| ------------------------------------------------------------ | -------- | ------------------------------ |
| {ユニットテストカバレッジ目標}以上                           | 良好     | 継続的に維持する               |
| {カバレッジ改善余地}以上で{ユニットテストカバレッジ目標}未満 | 改善余地 | 重要な部分から段階的に向上する |
| {カバレッジ改善余地}未満                                     | 要改善   | テスト不足の原因を分析する     |

### インテグレーションテストの基準

- 主要なエンドポイントすべてにテストを実装する
- 正常系と異常系の両方をテストする
- 権限チェックが必要な機能は、認証状態の違いをテストする
- CSRF保護が機能していることを確認する
- リダイレクトとフラッシュメッセージの動作を検証する

### E2Eテストの基準

- 主要なユーザーシナリオすべてにE2Eテストを実装する

### ユーザビリティテストの基準

評価は5段階で行い、次の観点を対象とします。

- 使いやすさ: 操作が簡単で分かりやすいか
- デザイン: 色、文字の読みやすさ、レイアウトなど視覚的な要素の分かりやすさ
- パフォーマンス: 操作に対するレスポンスの速さ、ストレスの有無
- アクセシビリティ: 高齢者や障がい者への配慮、視覚的な要素の分かりやすさ

| 評価 | 基準                                                           |
| ---- | -------------------------------------------------------------- |
| 5    | 操作が直感的で、パフォーマンスが非常に速い                     |
| 4    | 基本的に使いやすく、改善の余地がある                           |
| 3    | 操作に慣れが必要だが使え、パフォーマンスによるストレスは少ない |
| 2    | 使いにくく、パフォーマンスも遅い                               |
| 1    | 操作が複雑で、システムの動作が遅い                             |

評価結果に応じて、次の基準で改善します。

- 評価3以下: 改善を必須とする
- 評価4: 改善を検討する
- 評価5: 現状を維持する

### テストデータの基準

- 各テストは独立して実行でき、テスト間でデータを共有しない
- あるテストの成否が、他のテストの結果に影響を与えないようにする
