技術スタックの収集と整理
=========================

収集対象
-------------------------

設定ファイルを読み、プロジェクトで実際に使われている技術だけを拾います。

- `composer.json`: PHPバックエンド技術
- `package.json`: フロントエンド・JavaScript技術
- `Gemfile`: Rubyバックエンド技術
- `pyproject.toml`・`Pipfile`: Pythonバックエンド技術
- その他の設定ファイル: 開発支援ツール・CI/CD

カテゴリー
-------------------------

技術要素は次の4カテゴリーに分けます。

### バックエンド

- 言語
- フレームワーク
- 主要ライブラリ
- 静的解析ツール
- テストツール

### フロントエンド

- 言語
- フレームワーク
- 主要ライブラリ
- ビルドツール
- テストツール

### 開発ツール

- ローカル開発環境
- タスクランナー
- ドキュメンテーションツール

### CI/CD

- 継続的インテグレーション
- デプロイメント

技術要素ごとの情報
-------------------------

各技術要素について、確認できる範囲で次を書きます。

- 名称とバージョン
- プロジェクト内での主な用途・役割
- 設定ファイルの場所と重要な設定項目
- 関連する実行コマンドやスクリプト

バージョン管理方針
-------------------------

バージョン管理方針は、設定ファイルから判断できる事実と、ユーザーが決める方針を分けます。

- メジャーバージョンアップ: 判断基準と影響範囲の評価方法
- セキュリティアップデート: 適用タイミングと検証手順
- 依存関係管理: ライブラリ間の互換性確保方法

方針が既存文書にない場合は、AIが決めずに案を示し、ユーザーの確認を得ます。
確認が得られない場合は「未定」と書き、確認が必要な点を残します。

制約
-------------------------

- 設定ファイルの内容を確認するだけで、ファイルの修正は行いません。
- プロジェクトで実際に使用されている技術だけを書きます。
- 推測や想定に基づく情報は書きません。
- デプロイ環境の情報は対象外です。
- 新規技術の提案や追加は行いません。
- 機密情報や過度に詳細な実装方法は書きません。

エラーハンドリング
-------------------------

- 設定ファイルがない: 該当セクションを省略し、確認できなかった旨を書きます。
- バージョンが不明:「要確認」と書き、根拠のファイルを示します。
- 用途が不明: 設定ファイル内の記載だけを客観的に書き、推測しません。

出力
-------------------------

- 出力形式は`assets/technology.md`を正本とします。
- 出力前にテンプレートを読み、見出しの追加・削除・順序変更をしません。
- 出力後に見出しをテンプレートと突き合わせます。
