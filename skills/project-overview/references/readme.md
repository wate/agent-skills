READMEの作成
=========================

基本方針
-------------------------

READMEは、新規参加者が最初に読む入口です。
プロジェクトの全体像、セットアップ、使い方が分かるように書きます。
確認できない内容は書かず、必要な場合は「要確認」と明記します。

情報収集
-------------------------

次の情報を集めます。

- 依存関係ファイル: `composer.json`、`package.json`、`requirements.txt`、`Gemfile`等
- 既存文書: `docs/`、`README.*`、設計書、運用手順
- ビルド・実行設定: `Taskfile.yml`、`Makefile`、`docker-compose.yml`、CI設定
- ディレクトリ構成: 主要ディレクトリと主要ファイル
- テスト・Linter設定: テストコマンド、静的解析コマンド

種別の判定
-------------------------

### ソフトウェア開発向け

次のいずれかがある場合は、ソフトウェア開発向けと判定します。

- 依存関係ファイルとアプリケーションコード
- ビルド・テスト・デプロイの設定
- API、データベース、画面などの実装

### 業務改善向け

次のいずれかが中心で、アプリケーションコードがない場合は、業務改善向けと判定します。

- 要件定義書、業務フロー、ヒアリング資料
- 業務課題、改善提案、効果測定の資料
- プロジェクト計画、体制、予算

判定に迷う場合は、どちらの構成にするかをユーザーへ確認します。

ソフトウェア開発向けの構成
--------------------------

### 必須セクション

- プロジェクト名
- 概要: 何をするプロジェクトか
- セットアップ: 前提条件、インストール、初期設定
- 使い方: 起動、実行、主要コマンド

### 推奨セクション

- 主な機能
- 技術スタック
- ディレクトリ構成
- テスト
- 開発への参加方法
- ライセンス

### 書き方

- コマンドは実行可能な形で書きます。
- 環境変数は、値ではなく設定方法を書きます。
- 機密情報は書きません。
- 長い説明は`docs/`へリンクします。

業務改善向けの構成
-------------------------

### 必須セクション

- プロジェクト名
- 背景・課題: なぜこのプロジェクトを始めるか
- 目的・目標: 何を達成するか
- 対象範囲: 対象とする業務・組織・期間

### 推奨セクション

- ステークホルダー
- 業務フロー
- スケジュール
- 予算・体制
- リスクと対策
- 問い合わせ先

### 書き方

- 課題と目的を分けて書きます。
- 数値目標は、確認できた値だけを書きます。
- 法令や契約の解釈は書きません。
- 社外秘の情報は書きません。

最小生成の方針
-------------------------

- 情報がないセクションは省略します。
- 空の見出しだけを残しません。
- 推測した内容は「要確認」と書き、根拠を添えます。
- 既存のREADMEがある場合は、残す記述を確認してから更新します。

品質確認
-------------------------

- 新規参加者がセットアップから実行まで進めるか。
- 用語がプロジェクト内で統一されているか。
- コマンドとパスが実在するか。
- 機密情報が含まれていないか。
- 見出しがテンプレートと一致しているか。

出力
-------------------------

- ソフトウェア開発向けは`assets/readme-software.md`を正本とします。
- 業務改善向けは`assets/readme-business.md`を正本とします。
- 出力前にテンプレートを読み、見出しの追加・削除・順序変更をしません。
- 出力後に見出しをテンプレートと突き合わせます。
