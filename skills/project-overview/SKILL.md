project-overview
=========================

概要
-------------------------

プロジェクトの全体像を伝える次の2文書を作成・更新します。

- `README.md`: 新規参加者向けの入口。セットアップ、使い方、構成をまとめる
- プロジェクトブリーフ: 背景・目的・業務概要・期待効果をまとめる

READMEはソフトウェア開発向けと業務改善向けで構成を変えます。
新規作成と既存更新の両方に対応し、既存更新では差分確認を挟みます。

前提条件
-------------------------

- リポジトリのルートで実行します。
- 設定ファイル、既存文書、ディレクトリの読み取り権限があります。
- 出力先のディレクトリを作成できる権限があります。
- 既存文書を更新する場合は、差分を確認できる状態にします。

仕様
-------------------------

### 対象文書

| 文書                 | 内容                                         | 主な入力                             |
| -------------------- | -------------------------------------------- | ------------------------------------ |
| `README.md`          | プロジェクト概要、セットアップ、使い方、構成 | 設定ファイル、既存文書、ディレクトリ |
| プロジェクトブリーフ | 背景・目的、業務概要、期待効果、管理体制     | 既存文書、ユーザーへのヒアリング     |

この表は索引であり、テンプレートの代用ではありません。

### 出力先

- READMEはプロジェクトルートの`README.md`へ出力します。
- プロジェクトブリーフはユーザーの指定を優先し、指定がなければ`docs/index.md`へ出力します。
- 出力先のディレクトリがない場合は作成します。
- このリポジトリで検証用システムの文書を作る場合は、`docs/system/index.md`のように明示指定します。

### READMEの種別

リポジトリの内容から種別を判定します。

- ソフトウェア開発向け: 依存関係ファイルやアプリケーションコードがある
- 業務改善向け: 要件・業務フロー・ヒアリング資料が中心で、アプリケーションコードがない
- 判定に迷う場合は、どちらの構成にするかをユーザーへ確認します。

### 既存文書の扱い

1. 出力先に同名ファイルがある場合は、既存内容を読みます。
2. 生成案と既存内容の差分を示します。
3. ユーザーの承認を得てから更新します。
4. 承認がない場合は上書きしません。
5. `index.md`が仕様書索引の場合は、上書きするか別名にするかをユーザーへ確認します。

AIがリネームや上書きを自動で決めることはありません。

### テンプレート

出力形式は次のテンプレートを正本とします。
出力前に必ず読み込み、見出しの文言・順序・階層を一致させます。

- README(ソフトウェア開発向け): [assets/readme-software.md](assets/readme-software.md)
- README(業務改善向け): [assets/readme-business.md](assets/readme-business.md)
- プロジェクトブリーフ: [assets/project-brief.md](assets/project-brief.md)

見出しの追加・削除・順序変更・記憶による書き換えはしません。
`assets/`はテンプレートであり、出力先ではありません。

### カスタマイズ

- 出力先は依頼で指定できます。
- READMEの種別は依頼で指定できます。
- プロジェクトブリーフのヒアリング項目は、既存情報で足りる場合は省略できます。

手順
-------------------------

1. 依頼から対象文書を決めます。指定がなければ、READMEとプロジェクトブリーフを候補にします。
2. READMEは、依存関係ファイルとアプリケーションコードから種別を判定します。
3. プロジェクトブリーフは、既存文書から分かる情報を先に集めます。
4. 対象文書の`references/`と`assets/`を読みます。
5. 事実だけを使って生成案を作り、不足分だけをユーザーへ確認します。
6. 既存文書がある場合は差分を示し、承認を得ます。
7. 承認後に出力先へ書き、見出しをテンプレートと突き合わせます。

制約
-------------------------

- 確認できた事実だけを書きます。推測した内容は「要確認」と書きます。
- 法令や契約の解釈は書きません。正式名称と確認先だけを書きます。
- 機密情報(認証情報、APIキー、秘密鍵)を書きません。
- READMEは新規参加者向け、プロジェクトブリーフは背景・目的・業務概要に限定します。
- 役割宣言や、他のスキル・プロンプトの名前を書きません。

トラブルシューティング
-------------------------

- 既存情報が不足している: 分かる範囲で下書きを作り、不足分だけを1問ずつ確認します。
- READMEの種別が不明: ソフトウェア開発向けか業務改善向けかをユーザーへ確認します。
- `index.md`が仕様書索引: 上書きするか、別名にするかをユーザーへ確認します。
- 既存文書が手で編集されている: 差分を示し、残す記述を確認します。承認なしに上書きしません。

参照ファイル
-------------------------

- `references/readme.md`: READMEの情報収集、2種類の構成、必須セクション
- `references/project-brief.md`: プロジェクトブリーフの3フェーズ、ヒアリング項目、出力構成
